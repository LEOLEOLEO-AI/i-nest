# 大模型推理异构化：为什么GPU不能再包办一切？

### 🍳 为什么说GPU像"全能大厨"？

GPU算力虽强，但**大量时间耗在非计算环节**，硬件利用率被拉低。
- **传统衡量误区**：只看Tensor Core数量、显存大小、矩阵运算速度。
- **真实推理流程**：请求排队 → 查缓存 → 拼批次 → 存中间状态 → 反复取显存 → 跨机网络传输。
- **资源消耗不均**：有的阶段缺算力，有的缺显存带宽，有的缺内存容量，有的卡CPU调度或网络延迟。
- **核心矛盾**：把所有工作都压在高端GPU上，能跑但**不经济**。

### 🚰 一次推理请求到底分几步？

推理是**多步骤首尾相接的流水线**，瓶颈随阶段不断移动。
- **CPU调度阶段**：判断请求去向、等待队列、拼批次、查Prefix Cache。
  - 系统提示词、RAG文档等重复前缀可直接复用，不用重算。
- **Prefill阶段（读题）**：一次性读完输入，逐层处理并生成KV Cache。
- **Decode阶段（逐字作答）**：逐个预测Token，后一个依赖前一个，**天然串行**。
- **推测解码**：小模型先写草稿，大模型批量检查，猜对保留猜错重算。
  - 本质是新增了草稿模型、验证模型及两者调度关系。

### 📖 Prefill和Decode对硬件要求差在哪？

两者运行同一模型，但**一个吃算力一个吃带宽**，GPU利用率天差地别。

| 维度 | Prefill（读题） | Decode（写答案） |
| :--- | :--- | :--- |
| 处理对象 | 整段输入（几千Token） | 单个Token |
| 计算形态 | GEMM（矩阵×矩阵） | GEMV（矩阵×向量） |
| 瓶颈类型 | 计算密集 | 内存带宽密集 |
| GPU利用率 | 高，Tensor Core持续工作 | 低，计算单元等数据 |
- **Roofline Model**：由Samuel Williams、Andrew Waterman、David Patterson于**2009年**提出，核心看"每搬运一份数据能完成多少计算"。
  - 数据能反复用 → 受算力限制；每算一点都要取新数据 → 受带宽限制。

### ⚖️ Decode阶段GPU为什么会"等数据"？

Batch大小是核心杠杆，**吞吐与延迟天然矛盾**。
- **数据搬运层级**：HBM → 缓存 → 共享内存 → 寄存器 → Tensor Core，每一步都耗时。
- **训练/Prefill**：大Batch分摊权重读取成本，一次读出服务多Token。
- **在线Decode**：请求到达时间、长度不一，不能无限凑Batch。
  - Batch越大 → 单Token成本越低，但首Token延迟越高。
  - Batch越小 → 交互体验越好，但硬件利用率越低。
- **Continuous Batching**：请求结束后立刻补新请求进批次，但并发不够时仍频繁读显存。

### 💼 不同业务的推理瓶颈一样吗？

即使模型相同，**不同业务需要完全不同的推理集群**。
- **普通聊天**：输入输出中等，首Token延迟和生成流畅度都重要，Prefill和Decode都不能慢。
- **RAG/长文档问答**：输入几万Token，输出短，**Prefill压力大**。
- **长程Agent**：持续调用工具，KV Cache越积越多，关注缓存复用和总任务成本。
- **代码生成**：输出长，**Decode占比高**。
- **离线数据生成**：可接受大Batch，对单用户延迟不敏感，GPU利用率高。
- **评价指标升级**：从总吞吐（Token/s）转向**Goodput**——满足延迟要求的有效请求量。

### 📝 KV Cache为什么成了关键变量？

KV Cache是模型的"临时草稿纸"，**长上下文下占显存比例极高**。
- **定义**：保存前面各层Attention的Key和Value，后续生成直接读取，不用重算。
- **特点**：模型参数多请求共享，KV Cache是**每个请求单独一份**。
- **跨阶段问题**：Prefill和Decode分机部署时，KV Cache要跟着请求搬，增加网络等待。
- **Mooncake系统**：来自月之暗面Kimi服务，发表于**FAST 2025**。
  - 建立分布式KV Cache池，利用闲置CPU、DRAM、SSD存储，实现长前缀复用。
  - KV Cache开始像数据库数据，需要管理位置、复用、淘汰、搬运策略。

### 🔀 为什么要把Prefill和Decode分开部署？

两类请求互相干扰，**绑在一起无法独立扩容**。
- **传统同组部署**：简单，KV Cache不用搬，权重只存一份。
- **核心问题**：
  - 长Prefill占用大量算力 → Decode请求被挡住 → 用户感觉卡顿。
  - 扩容需求不同：Prefill缺计算吞吐，Decode缺带宽和并发。
- **DistServe方案**：发表于**OSDI 2024**。
  - 分配到不同GPU池，分别围绕首Token时间和单Token时间配置资源。
  - 根据网络带宽决定节点放置，避免KV Cache传输成新瓶颈。
  - 实验显示延迟约束下，单GPU承载有效请求量显著提升。
- **优化技巧**：逐层传输KV Cache，前几层算完就发，Prefill同时算后面层，把传输藏在计算里。

### 💾 不同显存类型怎么分工？

HBM不是所有阶段都用得满，**GDDR+HBM组合可能更划算**。
- **HBM特点**：高带宽、高成本，像紧挨着工厂的大仓库，Decode阶段刚需。
- **Prefill特点**：计算密集，输入足够长时瓶颈在计算单元，HBM峰值带宽未必用满。
- **HMA-Serve方案**：**2026年**提出。
  - GDDR加速器做Prefill，HBM GPU留做Decode。
  - 配套分阶段量化、逐层KV Cache传输、延后反量化，解决跨厂商跨精度协同。
  - 测试中Goodput和单位美元Goodput均更高。
- **异构判断标准**：不是芯片名字，而是算力、带宽、容量、价格是否匹配当前阶段。

### ⚡ SRAM为什么适合逐Token生成？

SRAM是"手边小料架"，**用容量换低延迟和高片上带宽**。
- **优势**：比HBM离计算单元更近，延迟更低、片上带宽更高，权重驻留后不用每Token去片外搬。
- **适合场景**：低并发、带宽受限的矩阵向量运算（即Decode）。
- **代价**：芯片面积占用大，单位容量远贵于DRAM/HBM，受光刻Reticle限制有容量硬上限。
- **局限**：模型放不下就要拆多芯片，引入片间通信问题。

### 🧠 PIM的思路是什么？

PIM（Processing-in-Memory）= **把加工设备放进仓库，减少数据搬运**。
- **核心逻辑**：Decode瓶颈不在计算慢，而在权重来回搬太费时间，在内存附近做运算可减少总线往返。
- **适合场景**：Memory Bound的算子。
- **现实限制**：
  - 内存附近计算单元通用性差，精度、编程、算子支持都受限。
  - 更现实的是PIM负责部分带宽敏感工作，GPU处理复杂控制和计算密集算子。
- **算子级拆分挑战**：Attention与MLP在Transformer每层紧密相连，分放不同芯片会导致中间结果反复传输，可能吃掉算子加速收益。

### 🛫 调度系统为什么像航空调度？

异构越细，调度越重要，**不能只看单段速度**。
- **阶段级拆分**：Prefill/Decode分离，边界清晰。
- **算子级拆分**：Attention偏带宽、MLP偏计算、MoE有跨设备通信，同一算子在不同输入长度、Batch、负载下最优硬件也不同。
- **DOPS方案**：**2026年**提出。
  - 不把阶段永久绑定设备，根据请求形状、设备拥堵、权重位置动态安排算子。
  - 同时考虑算子调度和分块权重布局，因为换设备要支付权重搬运和重排成本。

### 🤖 推测解码也是硬件分工吗？

推测解码本质是**把Decode拆成两种工作，对应两种硬件**。
- **Drafter（草稿）**：快速连续产生候选Token，重点是低延迟，适合小设备。
- **Verifier（验证）**：一次检查多个候选，计算规模大，适合大型GPU批量处理。
- **部署形态**：一个Drafter可服务多个Verifier，摊薄成本。
- **计算形态改变**：普通Decode每轮验证1个Token（极端GEMV），推测解码一次验证多个（往小规模矩阵计算拉）。
  - 算法优化和异构硬件互相影响：算法改变算力/带宽需求，硬件配置反过来影响最优算法参数。

### 🎛️ 异构系统真正难在哪？

硬件拆开只是开始，**调度和网络才是核心挑战**。
- **Runtime调度复杂度**：
  - 要知道请求该去哪、哪台机器空闲、KV Cache在哪、搬过去要多久、有没有前缀缓存、网络堵不堵、设备有没有对应权重。
  - 同构集群假设每台机器能力接近，异构下这个假设消失。
  - 分工不能僵化：Prefill队列满而Decode池空时，应允许动态调整。
- **网络容易吃掉收益**：
  - 阶段分离搬KV Cache，算子分离搬Hidden State，推测解码交换候选和结果。
  - 芯片内部省几十微秒，一次跨服务器传输可能全花回去。
  - 节点摆放：同机用NVLink等高速互联，跨机走网卡交换机，距离越远扩容越灵活但传输成本越高。

### 💰 异构一定比纯GPU便宜吗？

不一定，**总拥有成本才是最终衡量标准**。
- **规模不经济**：请求量小时，拆开后两组设备都吃不满，产生资源碎片。
  - 输出短 → Decode节点长期空闲；输入短 → Prefill池利用率不足。
- **隐性成本**：多一种芯片就多一套驱动、编译器、监控；跨厂商还要统一KV Cache格式、量化方式、错误处理。
- **最终指标**：满足用户体验前提下，**每个Token的总成本**（芯片+内存+网络+功耗+散热+闲置率+软件复杂度）。
- **没有通用最优解**：在线助手愿为流畅交互付更高成本，离线生成追求整体吞吐。

### 🔮 推理系统未来会变成什么样？

推理系统正从"GPU服务器阵列"变成**数据流驱动的生产线**。
- **训练集群**：追求同构，型号、互联、软件栈一致，方便大规模同步计算。
- **推理集群**：走向异构分工——
  - CPU：接收组织请求
  - 计算型GPU：长输入Prefill
  - 高带宽GPU/SRAM加速器：Decode
  - DRAM/SSD：分层KV Cache存储
  - 网卡交换机：状态迁移
  - Runtime：根据请求长度、缓存位置、实时负载动态调度
- **GPU定位变化**：不会被淘汰，大规模矩阵乘法、Prefill、MLP、批量验证、通用算子仍依赖GPU成熟生态，但不再包办全部工作。
- **未来核心竞争力**：不是单卡最高FLOPS，而是系统最清楚一个Token什么时候需要计算、什么时候需要带宽、什么时候只需要把数据留在正确位置。
