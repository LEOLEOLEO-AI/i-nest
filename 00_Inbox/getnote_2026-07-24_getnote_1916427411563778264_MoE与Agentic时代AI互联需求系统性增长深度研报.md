# MoE与Agentic时代AI互联需求系统性增长深度研报

### 🏆 核心背景与核心洞察

AI基础设施的核心关注点已从单一芯片算力（FLOPS）转向全系统数据协同效率：GPU为计算大脑，HBM/DRAM/SSD/HDD构成记忆体系，CPU负责任务调度，光互联/网络/互连技术则是系统的神经与四肢。大脑算力再强，若数据传输链路存在瓶颈，整个系统将陷入等待空转。
本文以数学推导+工程实测数据为基础，系统性拆解MoE架构对互联需求的底层驱动逻辑，以及Agentic场景下互联需求的指数级放大效应，最终映射到未来数据中心硬件BOM的结构性变化。

### 📊 不同场景互联需求倍率总览

| 场景 | Interconnect需求倍率 | 主要原因 |
| :--- | :--- | :--- |
| **Dense chatbot inference** | 1× | 主要瓶颈在HBM读取权重、KV Cache和少量Tensor Parallel通信 |
| **MoE chatbot inference** | 3-10× / token | 每个MoE层都要做Expert Dispatch + Combine；通信从规则All-Reduce变成高熵All-to-All |
| **MoE training** | 2-5×系统级网络压力，局部光互连/交换机内容可达4-6× | MoE层All-to-All占用越来越多step time；Google/TPU路线已把DCN从1个ToR扩展到4-6个in-rack switches |
| **Agentic MoE inference** | 50-300×有效interconnect需求 | 10-30× token使用量 × 3-10× MoE per-token网络强度 × KV迁移/多智能体扇出/常驻状态开销 |
| **极端multi-agent + long-context + disaggregated serving** | 100-500×也并不离谱 | 并非MoE单一因素驱动，而是MoE、Agent循环、长上下文、KV迁移、并发分支多因素叠乘 |

### 🔍 Dense Transformer时代的通信特征

Dense Transformer的通信模式具备**规则、静态、可预测**的核心特性，编译器可在训练前完成全链路通信调度，硬件资源利用率接近理论上限：
1.  **模型结构拆分**：标准Transformer Block分为Attention（token间信息交互，通信密集）和FFN/MLP（单token非线性变换，计算密集）两部分，所有token共享同一组FFN权重，无动态路由逻辑。
2.  **三大经典并行策略**：
    | 并行模式 | 核心逻辑 | 通信特征 |
    | :--- | :--- | :--- |
    | **Data Parallelism (DP)** | 单GPU持有完整模型副本，处理不同batch切片，step末尾通过All-Reduce同步梯度 | 通信发生在step末尾，可与反向传播重叠，对延迟不敏感 |
    | **Tensor Parallelism (TP)** | 将大矩阵算子切分到多GPU协同计算，每层计算完成后合并结果 | 通信发生在前向路径中，对延迟敏感，通常限制在NVLink域内部署 |
    | **Pipeline Parallelism (PP)** | 将模型按层切分为多段，分配到不同GPU执行，层间传递中间结果 | 通信量小，需处理Pipeline Bubble（流水线空泡）问题 |
3.  **通信模式本质**：Dense时代主流采用DP+TP+PP的3D并行组合，所有通信均为规则的All-Reduce类操作，天然适配Ring/Torus拓扑，可实现接近100%的链路带宽利用率。

### 🧩 MoE架构的核心逻辑与通信变革

MoE（Mixture of Experts，混合专家模型）通过"总参数与激活参数解耦"实现算力效率跃升，但彻底打破了Dense时代通信的规则性：
1.  **MoE经济性来源**：总参数决定模型知识容量上限，激活参数决定单token实际计算成本。例如DeepSeek V4-Pro总参数达1.57T，但单token仅激活7个Expert，激活参数仅49B，稀疏度达32×。GShard 2020年实测显示，模型参数从37.5B扩至600B（16×增长），端到端训练成本仅从6 TPU v3 core-years增至22 TPU v3 core-years（约3.6×增长）。
2.  **主流开源MoE模型参数对比**：
    | 模型 | 总参数 | 激活参数 | 稀疏度 | Expert数 | Top-K激活数 |
    | :--- | :--- | :--- | :--- | :--- | :--- |
    | GShard MoE (2020) | 600B | ~1.5B | 400× | 128-2048 | 2 |
    | Mixtral 8x7B | 47B | 13B | 3.6× | 8 | 2 |
    | Qwen3-235B-A22B | 235B | 22B | 11× | 128 | 8 |
    | DeepSeek V3 / V3.2 | 671B | 37B | 18× | 256+1 | 8+1 |
    | Kimi K2 / K2.6 | 1.04T | 32B | 33× | 384 | - |
    | DeepSeek V4-Pro | 1.57T | 49B | 32× | 384+1 | 6+1 |
3.  **MoE通信本质：All-to-All的必然性**：MoE前向传播的Dispatch（token分发到对应Expert）和反向Combine（Expert结果回传token源设备）两步操作，在张量代数层面天然要求"每个节点向所有节点发送数据"的All-to-All通信模式，不存在绕开该通信的工程方案。
4.  **All-Reduce vs All-to-All复杂度差异**：
    - All-Reduce的时间复杂度为O(1)，节点数从16扩至2048时，通信耗时基本维持在1000μs左右。
    - All-to-All的时间复杂度为O(√D)（D为设备数量），节点数从16扩至2048时，通信耗时从500μs增至4500μs，增长约9倍。
    - GShard实测显示，Expert数从128扩至2048时，整体设备时间仅增长1.7×，但Dispatch+Combine通信时间增长3.75×，通信在总执行时间中的占比从16%升至36%。

### 🌐 网络拓扑与对分带宽的数学逻辑

MoE的All-to-All通信对网络核心指标**Bisection Bandwidth（对分带宽）**提出极高要求，直接驱动网络拓扑向高维方向演进：
1.  **对分带宽定义**：将集群从中间对半切分后，两侧节点间可同时传输的最大数据量，决定了极端流量场景下的网络承载能力。All-to-All通信天然会打满集群对分带宽。
2.  **不同维度Torus拓扑的对分带宽特性**：
    | Torus维度 | 对分带宽缩放公式 | 百万节点规模下拥塞压力 |
    | :--- | :--- | :--- |
    | 3D Torus | N^(2/3) | ~100× |
    | 4D Torus | N^(3/4) | ~31.6× |
    | 5D Torus | N^(4/5) | ~15.8× |
    | 6D Torus | N^(5/6) | ~10× |
    维度越高，对分带宽越接近线性扩展，拥塞压力随节点数增长的速度越慢。这正是Google TPU从3D Torus向4D-6D Torus演进的核心数学动因。
3.  **MoE场景下的拓扑选型趋势**：传统3D Torus已无法支撑大规模MoE集群的All-to-All流量，行业正向Clos（Fat Tree，线性对分带宽）、高维Torus、Dragonfly等拓扑迁移，直接带动交换机、光模块硬件需求爆发。
4.  **MoE的长尾延迟痛点**：MoE层必须等待所有选中的Expert返回结果才能进入下一层，Top-K激活模式下，单Expert的长尾延迟会被K次方放大，对网络最差路径延迟、拥塞控制、冗余路径设计提出远高于Dense场景的要求。

### 📐 MoE通信量数学推导与实测

通过标准化公式可精准量化MoE的通信开销：
> 单token MoE前向通信总量 ≈ 2 × K × H × b × r × L_moe
> 其中K为单token激活Expert数，H为隐层维度，b为数据精度字节数，r为远端Expert占比，L_moe为MoE层数。

主流MoE模型单token通信量实测结果：
| 模型 | 单token MoE通信量 | 核心参数 |
| :--- | :--- | :--- |
| Mixtral 8x7B | ~840 KB | H=4096, K=2 |
| Qwen3-235B-A22B | ~10 MB | K=8 |
| DeepSeek V3 / V3.2 | ~11 MB (BF16) / 5.5 MB (FP8) | H=7168, K=8 |
| DeepSeek V4-Pro | ~4.1 MB (FP8) | H=7168, K=6，通过FP8精度+降低Top-K数大幅压缩通信量 |

### 🚀 训练与推理阶段的互联需求差异
1.  **Training阶段**：MoE训练的All-to-All通信发生在前向路径中，无法像Dense训练的梯度同步那样作为后台操作与反向传播重叠。同等有效训练吞吐下，MoE训练的系统级网络压力是Dense的2-5倍，局部机架内网络压力可达4-6倍。Google TPU下一代路线已规划将每机架in-rack交换机从1个增至4-6个，以吸收MoE的通信溢出。
2.  **Inference阶段**：MoE推理的通信痛点集中在Decode阶段，每生成1个token，模型每经过1层MoE就会触发2次All-to-All通信。以60层MoE的DeepSeek V3/V4为例，单token生成过程将触发120次Collective通信，高频小包传输是网络最难优化的场景之一。行业主流通过PD分离（Prefill-Decode Disaggregation）、Attention/MoE节点分离等架构优化，将不同计算特征的任务分配到专属硬件集群，提升整体GPU利用率。

### 🤖 Agentic场景的互联需求指数级放大

Agentic工作流通过5个独立放大器，将有效互联需求在MoE基础上进一步放大数十至数百倍：
1.  **Token Loop Multiplier（10-30×）**：普通Chatbot单次交互仅需数百token，而Agent任务（如代码调试）会形成多轮调用循环，总token量可达200K-500K，是普通对话的10-30倍。
2.  **MoE Per-Token Multiplier（3-10×）**：MoE单token的网络强度天然是Dense模型的3-10倍。
3.  **KV Cache Mobility（1-2×）**：Agent场景下KV Cache从单次对话的短期缓存变为跨多轮调用的持久化工作记忆，频繁发生跨节点迁移、共享、召回操作，新增大量东西向流量。
4.  **Multi-Agent Fanout（2-10×）**：Agent系统常通过多子任务并行探索提升效率，单次用户请求可派生出2-10个并发模型调用。
5.  **Always-On冗余开销**：Agent作为生产级工作流，对排队、延迟抖动的容忍度极低，迫使集群为峰值负载预留冗余网络容量，进一步拉高网络资源投入。

### 💰 硬件层受益链条全景映射

MoE与Agentic场景的互联需求爆发，将驱动全栈硬件BOM的结构性升级：
| 硬件层 | MoE / Agentic的影响 | 主要受益厂商 |
| :--- | :--- | :--- |
| **GPU/TPU** | 单Expert算力需求降低，但整体需要更多算力卡支撑大规模Expert部署 | NVDA, GOOG, AMD |
| **Scale-up Network (NVLink/ICI)** | 域规模扩大，带宽需求持续提升 | NVDA NVSwitch, Marvell SerDes |
| **Scale-out Network (DCN)** | 交换机、端口、光收发器数量大幅增加 | NVDA Quantum/Spectrum, ANET, CSCO |
| **Optical Transceiver** | 速率从800G向1.6T、3.2T演进，部署数量翻倍 | COHR, LITE, AAOI, Innolight |
| **CPO（共封装光学）** | 长期逐步替代可插拔光模块，解决功耗与信号完整性瓶颈 | TSMC, Lumentum, Coherent, Tower Semi |
| **PCB / Substrate** | 尺寸更大、布线密度更高、信号速率更快 | Ajinomoto (ABF), Mitsui Kinzoku (HVLP), Elite (CCL), Unimicron |
| **Retimer / SerDes** | 部署数量随信号速率指数增长 | ALAB, CRDO, MRVL, AVGO, Montage |
| **CXL / PCIe** | 实现内存池化，释放MoE Expert的存储部署灵活性 | ALAB, Montage, AVGO |
| **Power** | 供电架构从54V向800V升级 | Wolfspeed, Onsemi, Infineon, LOTES, FIT |
| **Liquid Cooling** | 高密度机架部署的刚性需求 | Vertiv, CoolIT |
