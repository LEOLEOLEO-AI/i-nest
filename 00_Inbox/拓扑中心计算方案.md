# 拓扑中心计算方案

明白了，TCC 是 **Topology-Centric Computing（拓扑中心计算）**，不是传输层拥塞控制。我重新基于这个定义来做方案——核心思路是：**在 NCCL 成熟的集合通信能力基础上，融合软件定义互联（SDI）的全局拓扑可编程能力，发展出以拓扑为中心的新型计算范式 TCC**，让通信拓扑不再是计算的约束，而成为可以被软件动态定义、与计算协同优化的一等资源。

下面是完整方案。

---

## 一、总体架构与核心理念

### 1.1 为什么要从 NCCL 走向 TCC

NCCL 解决的是"给定硬件拓扑下，如何把集合通信跑满带宽"的问题。它通过拓扑发现、Ring/Tree 算法、多协议优化，在固定拓扑上实现了接近硬件上限的通信效率 。

但 NCCL 的本质是**被动适配拓扑**——拓扑是硬件给定的，软件只能"发现"和"利用"，不能"定义"和"重塑"。

拓扑中心计算（TCC, Topology-Centric Computing）的理念正好反过来：**拓扑不再是约束，而是可以被软件动态编排的资源**。通过软件定义互联（SDI）技术，物理层、数据链路层、网络层全维可定义 ，计算任务可以根据自身通信模式"定制"最优拓扑，实现"以算定网、以网促算"的协同优化。

这与软件定义晶上系统（SDSoW）的思路一脉相承——在晶圆级异构集成场景下，数千个芯粒的互连本身就是可软件定义的，拓扑中心计算是晶上系统架构的自然延伸 。

### 1.2 总体架构：三层协同

```
┌─────────────────────────────────────────┐
│         应用层：AI 框架 / 并行计算        │  ← 完全兼容 NCCL API
├─────────────────────────────────────────┤
│     TCC 协同层（拓扑中心计算引擎）        │  ← 核心新增
│  ┌─────────┬──────────┬──────────────┐  │
│  │拓扑编排  │通信-计算  │ 拓扑感知      │  │
│  │引擎      │协同调度   │ 任务映射      │  │
│  └─────────┴──────────┴──────────────┘  │
├─────────────────────────────────────────┤
│     SDI 控制面（软件定义互联控制器）      │  ← 新增
│  全局拓扑管理 · 流量调度 · 路径重配置     │
├─────────────────────────────────────────┤
│     NCCL 数据面（继承 + 扩展）           │  ← 继承为主
│  集合通信原语 · Ring/Tree 算法 · 多协议  │
├─────────────────────────────────────────┤
│     硬件层：GPU/NIC/交换机/晶上互联       │
└─────────────────────────────────────────┘
```

关键转变：NCCL 是"**拓扑→通信**"的单向优化，TCC 是"**计算↔拓扑↔通信**"的闭环协同。

## 二、核心功能模块

### 2.1 NCCL 基础层（继承 + 北向扩展）

**定位：** 保留 NCCL 全部能力，作为 TCC 的数据面执行引擎。

**继承内容：**
- 全部集合通信原语：All-Reduce / All-Gather / Reduce-Scatter / Broadcast / Reduce / P2P 
- 拓扑发现与建模能力（PCIe/NVLink/NVSwitch/InfiniBand/RoCE）
- Ring / Tree / 分层（Hierarchical）通信算法
- Simple / LL / LL128 三种协议 
- 网络插件机制（Transport Plugin）

**扩展内容：**
- **拓扑注入接口**：允许上层（TCC 引擎）主动"写入"拓扑信息，替代 NCCL 默认的自动探测结果——这是 TCC 能"定义拓扑"的关键入口
- **算法策略回调**：允许 TCC 引擎根据全局拓扑状态干预 NCCL 的算法选择（Ring vs Tree、通道数、分块大小等）
- **动态拓扑重配钩子**：运行时支持拓扑变更通知与通信重建

**工作量（软件）：** 约 4-5 人月。核心是拓扑注入接口和策略回调的设计，不改动 NCCL 内核逻辑。

### 2.2 SDI 网络控制器（软件定义互联控制面）

**定位：** 全局拓扑资源的统一编排者，是 TCC 的"拓扑操作系统"。

**核心模块：**

1. **全局拓扑数据库**
   - 实时采集全网设备（GPU、NIC、交换机、链路）的连接关系与状态
   - 支持多粒度拓扑视图：物理拓扑、逻辑拓扑、虚拟拓扑
   - 晶上场景扩展：芯粒级 NoC 拓扑、硅光互联拓扑 

2. **拓扑编排引擎**
   - 根据计算任务的通信模式，生成最优虚拟拓扑
   - 支持拓扑模板库：Ring 拓扑、Tree 拓扑、Mesh 拓扑、Fat-Tree、超立方体等
   - 多任务拓扑隔离与资源划分

3. **路径与流量调度**
   - 基于 OpenFlow/P4Runtime 向可编程交换机下发流表
   - 支持动态重路由、带宽预留、多路径负载均衡
   - 时间感知调度（TaSDN）：为同步密集型集合通信提供确定性时延保障 

4. **Telemetry 与状态反馈**
   - 实时链路利用率、队列深度、时延分布
   - 向 TCC 协同层反馈网络状态，支撑拓扑重配置决策

**工作量（软件）：** 约 12-15 人月。
- 控制器框架（基于开源 SDN 控制器或自研轻量版）：5 人月
- 拓扑数据库与采集：3 人月
- 拓扑编排引擎：3 人月
- 路径调度与接口：2-4 人月

### 2.3 TCC 拓扑中心计算引擎（核心创新层）

**定位：** 连接计算任务与网络拓扑的"大脑"，实现计算-拓扑-通信的协同优化。

**核心模块：**

1. **通信模式分析器**
   - 静态分析 + 运行时 profiling：识别计算任务的通信特征
   - 分类维度：集合通信类型分布（All-Reduce 占比、All-to-All 占比）、消息大小分布、通信-计算比、同步频率
   - 支持并行策略识别：数据并行、张量并行、流水线并行、MoE 并行 

2. **拓扑-算法匹配引擎**
   - 为不同通信模式匹配最优拓扑形态：
     - 数据并行 All-Reduce → Ring / 分层 Ring 拓扑
     - 张量并行 All-Gather → Mesh / 全互连拓扑
     - MoE All-to-All → 胖树 / 全互连拓扑
     - 流水线并行 → 线性链拓扑
   - 输出最优拓扑模板 + NCCL 算法参数建议

3. **拓扑感知任务映射器**
   - 将计算任务（GPU 进程 / 芯粒）映射到物理拓扑上，使通信密集的进程在拓扑上邻近
   - 类似 NCCL 的拓扑感知，但维度从"单机内路由"扩展到"全网级任务放置"
   - 支持动态迁移（运行时根据通信模式变化调整进程位置）

4. **运行时拓扑重配控制器**
   - 根据训练阶段变化（如前向/反向/重计算不同阶段通信模式不同），动态切换拓扑
   - 与 NCCL 的 communicator 重建机制联动
   - 重配开销最小化：增量调整、预配置、热切换

5. **拓扑-计算协同优化器**
   - 联合优化计算并行策略和网络拓扑，不只是"给定计算优化通信"，而是"两者联合寻优"
   - 目标函数：端到端训练吞吐 / 时延 / 能效
   - 可选：基于强化学习的自适应策略

**工作量（软件）：** 约 15-18 人月。
- 通信模式分析器：3 人月
- 拓扑-算法匹配引擎：3-4 人月
- 任务映射器：3 人月
- 运行时重配控制器：3-4 人月
- 协同优化器：3-4 人月

### 2.4 晶上系统 TCC 适配层

**定位：** 将 TCC 理念落地到晶上系统（SDSoW）场景，是 TCC 区别于传统数据中心 SDN 的差异化方向。

**核心模块：**

1. **晶上网络抽象层**
   - 统一抽象 NoC、芯粒间互联、硅光互联、2.5D/3D 封装互联等多种介质 
   - 支持晶圆级数千芯粒的拓扑建模

2. **应用驱动的动态架构重构（ADR）**
   - 对应 SDSoW 中的 ADR 范式：根据应用需求实时重构晶圆级资源拓扑 
   - TCC 引擎直接驱动晶上互联的开关矩阵，实现芯粒级拓扑重配

3. **异构计算单元拓扑编排**
   - CPU 芯粒、GPU/NPU 芯粒、存储芯粒、专用加速芯粒的拓扑组织
   - 支持"按需组装"异构计算拓扑

**工作量（软件 + 硬件协同）：** 约 12-15 人月。
- 晶上网络抽象层：4 人月
- ADR 控制逻辑：4-5 人月
- 异构编排：4-6 人月（含硬件接口适配）

## 四、实施计划（四阶段，共约 20 个月）

### 第一阶段：拓扑注入 + 概念验证（第 1-4 个月）

**目标：** 验证"软件定义拓扑 → NCCL 利用拓扑"这条技术路径的可行性。

- 搭建 2 机 16 卡测试环境
- 实现 NCCL 拓扑注入接口（替代自动探测）
- 实现基础版 SDI 控制器（静态拓扑配置）
- 在 All-Reduce 场景下，对比"自动探测拓扑"vs"手动优化拓扑"的性能差异
- **里程碑：** 证明拓扑可被软件定义且能带来性能收益，MVP 验证通过

**投入：** 6-8 人。

### 第二阶段：SDI 控制面 + 拓扑编排（第 5-10 个月）

**目标：** 建成完整的 SDI 控制面和拓扑编排能力。

- 开发 SDI 网络控制器（拓扑数据库 + 编排引擎 + 路径调度）
- 支持动态拓扑重配（运行时切换拓扑形态）
- 实现拓扑模板库（Ring/Tree/Mesh/Fat-Tree 等）
- 在 8 机 64 卡规模下验证多种集合通信场景
- **里程碑：** 拓扑可动态切换，切换时间 < 100ms；典型场景下通信性能提升 10%-20%

**投入：** 10-12 人。

### 第三阶段：TCC 协同引擎 + 计算-拓扑闭环（第 11-16 个月）

**目标：** 实现计算-拓扑-通信的全链路协同优化。

- 开发通信模式分析器和拓扑-算法匹配引擎
- 实现拓扑感知任务映射器
- 开发运行时拓扑重配控制器
- 与 PyTorch 等主流框架集成，在真实大模型训练任务中验证
- **里程碑：** 在 GPT-3 级 / MoE 模型训练中，端到端吞吐提升 15%-30%（取决于通信占比）

**投入：** 12-15 人。

### 第四阶段：晶上场景扩展 + 生态化（第 17-20 个月）

**目标：** TCC 向晶上系统场景迁移，形成晶上拓扑中心计算方案。

- 晶上网络抽象层 + ADR 控制逻辑
- 晶圆级异构芯粒拓扑编排仿真验证
- 开源 TCC 核心模块（以 NCCL 插件 + SDI 控制器形式）
- 发布 TCC 技术白皮书与晶上场景路线图
- **里程碑：** 晶上场景 FPGA 仿真验证通过，开源社区初步建立

**投入：** 10-12 人。

## 六、关键技术风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| 拓扑重配开销过大，抵消收益 | 高 | 第一阶段就量化重配时延；设计增量重配、预配置、热切换机制；只在训练阶段切换时触发 |
| NCCL 内部接口不稳定 | 中 | 采用 Plugin + 拓扑注入的非侵入式设计，不依赖 NCCL 内部 API |
| 真实 workload 通信模式变化快 | 中 | 分层策略：粗粒度（训练阶段级）+ 细粒度（迭代级）分级处理 |
| 可编程交换机部署门槛高 | 中 | 支持纯软件拓扑模拟（用 VLAN/overlay 模拟拓扑变更），降低验证门槛 |
| 晶上场景硬件流片周期长 | 高 | 前期用 FPGA + 仿真验证，与晶上制造路线图对齐分阶段落地 |

## 七、与 NCCL 的关系定位

一句话总结：**NCCL 是 TCC 的数据面执行引擎，TCC 是 NCCL 的"拓扑大脑"**。

- 向下：TCC 完全继承 NCCL 的通信优化能力，不重复造轮子
- 向上：TCC 把"拓扑可编程"能力暴露给计算框架，开启新的优化空间
- 向外：TCC 天然适配晶上系统场景，是 NCCL 从"板级/机架级"走向"晶圆级"的关键跃迁
