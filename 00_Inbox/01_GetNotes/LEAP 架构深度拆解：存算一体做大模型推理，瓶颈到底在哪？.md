# LEAP 架构深度拆解：存算一体做大模型推理，瓶颈到底在哪？

### **这篇论文核心做了件什么事？**

把**存内计算、近存计算、网内计算**三种能力整合到同一张片上网络，专门加速大模型推理。
- **核心产物**：LEAP 硬件架构 + 划分-映射-调度软件框架
- **对标数据**：13B 模型上，吞吐比 H100 高 **1.52 倍**，能效高 **24.9 倍**
- **论文来源**：新加坡国立大学，arXiv:2609.00857，ICCAD 2025 扩展版

### **存内计算做大模型推理，硬件卡在哪？**

**两类核心挑战**，单靠 IMC（存内计算）本身解决不了。
- **挑战一：数据混合动态性**
  - **DSMM（静×动矩阵乘）**：静态权重 × 动态激活，IMC 天然适配（权重写进阵列不动）
  - **DDMM（动×动矩阵乘）**：两个动态矩阵相乘，IMC 没法做（操作数都在变）
  - 注意力层两种都有（Q/K/V/O 投影是 DSMM，QKT、attention×V 是 DDMM），FFN 全是 DSMM
  - 业界普遍走 **IMC + X** 路线，用近存计算或数字逻辑补 DDMM 短板

- **挑战二：大矩阵切分后的通信瓶颈**
  - 大矩阵切碎到大量 PE 上 → 输入要广播、部分和要归约
  - 归约器分配不均 → 热点节点拖死整体性能
  - 论文解法：**网内计算（INC）**，把算术逻辑做进路由器，归约在路上完成

### **软件侧的坑为什么更难填？**

硬件越异构，软件搜索空间越大，还要兼顾服务侧的指标冲突。
- **软件挑战一：三维耦合优化**
  - 矩阵划分 + 空间映射 + 数据流路由，三者互相耦合
  - 再叠上 IMC + NMC + INC 三层异构，搜索空间直接爆炸

- **软件挑战二：Prefill / Decode 诉求相反**
  - **Prefill**：计算密集，吃算力
  - **Decode**：带宽受限，吃存储带宽
  - 业界两条路：时间上 PD 均衡（掺着调度）、空间上 PD 分离（分资源池）

- **论文定位**：首次在以 IMC 为中心的架构上，把 **operation / phase / request** 三层 LLM 推理放一起分析

### **LEAP 硬件长什么样？**

一个 macro 同时承担三种角色，分工明确。
- **基本单元 = Macro**：PE + 路由器，通过 2D mesh NoC 互联
- **路由器里塞了两样东西**：
  - **NMC 资源**：scratchpad（存动态数据）+ 矩阵乘逻辑
  - **INC 资源**：归约逻辑，计算单元叫 **IRCU（路由器内计算单元）**
- **三种资源分工**：
  - IMC PE → 存静态权重、做 DSMM
  - 路由器 scratchpad → 存 KV cache、中间矩阵
  - IRCU → 做 DDMM + 部分和归约

- **两种工作模式**：

| 模式 | 配置 | 适用场景 |
| :--- | :--- | :--- |
| LEAP-A（聚合） | 所有 macro 同构，都带 IMC + 路由器 | prefill / decode 共享硬件 |
| LEAP-D（分离） | 分 prefill 区（同 LEAP-A）+ decode 区（砍掉 IMC，scratchpad 翻倍） | 优化 decode 带宽 |
- **关键硬件参数（Llama 3.2-1B）**：
  - Tile 数 64，每 tile 4 channel，每 channel 32 RPU，每 RPU 8 macro
  - Crossbar 128×128，8-bit；scratchpad LEAP-A 32KB / LEAP-D 64KB，16-bit
  - 路由器 buffer 256B，封包 64-bit，MAC 数 16

### **划分与映射是怎么做的？**

类似张量并行 + 上下文并行，但粒度细到亚 tile 级。
- **静态权重划分**：按 IMC PE 尺寸 128×128 切分
- **动态矩阵划分**：按 IRCU 带宽 + scratchpad 容量切分
- **映射三条启发式规则**：
  1. 同一矩阵的子矩阵落在连续区域
  2. 区域尽量是矩形，避免不规则拥塞
  3. 子矩阵按行主序或列主序排布

- **注意力层映射结果**：落在边长为 **2⌈D/C⌉** 的方形 macro 区域（D=嵌入维度，C=crossbar 尺寸）
  - Q/K/V 按列主序排，O 按行主序排
  - V 在 tile 内转置，tile 间不转置

- **KV cache 映射**：循环存储，token 向量循环追加进 scratchpad，保证各 macro 存储利用率均衡
- **层间映射**：**蛇形拓扑**，让首尾 decoder 物理相邻，缩短自回归回传路径
  - Llama 每层 = 1 注意力 + 3 FFN，FFN 隐藏维度 ≈ 4× 嵌入维度 → 每层 IMC 容量需求相同，规划规整

### **数据流有什么特别之处？**

**编译期完全确定**，运行时不需要动态仲裁。
- **7 种集合通信原语**：

| 原语 | 执行单元 | 核心功能 |
| :--- | :--- | :--- |
| Broadcast | / | 广播输入 |
| Reduce / ReduceScatter | IRCU | 归约部分和 |
| AllReduce / AllGather | IRCU | 全局汇总 / 收集 |
| E-ReduceScatter（逐元素） | IRCU | 逐元素归约散射 |
| MAC | IMC / IRCU | 乘加运算 |
- **核心设计取舍**：划分映射确定后，所有数据流模式固定，编译期就排好
  - 砍掉运行时控制和仲裁的硬件代价
  - 避免动态路由的不可预测拥塞
  - 说白了，就是用编译时的规划换硬件的简单和可预测性

- **LEAP-A Prefill 流程**（7 步）：
  Broadcast-1 → MAC-1 → ReduceScatter-1 → AllGather-1 + MAC-2 → AllReduce → AllGather-2 + MAC-3 → AllGather-3 + MAC-4 + ReduceScatter-2
  - 计算和通信能并行的环节全用流水叠起来

- **LEAP-A Decode 变化**：每次只处理 1 个 token，ReduceScatter 退化成 Reduce → 流水线填不满 → 吞吐比 prefill 低 **4~6 倍**

### **PD 分离具体怎么实现？**

把 decode 区的 IMC 全拆掉，省出的面积全给 scratchpad。
- **LEAP-D 核心思路**：
  - 权重只存在 prefill 区，KV cache 只存在 decode 区
  - KV 搬运和 prefill 的 AllGather 步骤完全重叠，**关键路径无额外开销**
  - decode 区 macro 更多 → 并发 scratchpad 访问更多 → 有效存储带宽更高

- **与其他 PD 分离方案对比**：

| 系统 | 迭代级分离 | KV 搬运 | 算子级分离 |
| :--- | :--- | :--- | :--- |
| LEAP | ✓ | ✓ | ✓（注意力层分离，其余聚合） |
| Adrenaline | ✓ | ✓ | ✓（投影+FFN 分离，注意力聚合） |
| DistServe | ✓ | ✓ | × |
| Sarathi | ✓ | × | × |
- **批处理设置**：batch size = 2，作者界定为**边缘场景适用**
  - 前一请求 decode 卸载到 decode 区后，prefill 区立即启动下一请求 prefill
  - 两请求抢 prefill 区权重时：撞上注意力算子 → decode 等；撞上投影算子 → 掐停投影让 decode 优先

### **实验结果到底怎么样？**

能效领先一到两个数量级，但也有明确的边界条件。
- **面积 / 功耗拆解（最反常识的结论）**：

| 组件 | 面积占比 | 功耗占比 |
| :--- | :--- | :--- |
| IMC PE | 72.06% | 20.15% |
| Scratchpad | 10.43% | 23.53% |
| 路由器 | **17.51%** | **56.32%** |
- 路由器只占不到两成面积，却吃掉超过一半功耗
  - 说白了，计算下沉到存储后，省下来的 DRAM 访问能耗，又以片上互联的形式还回来了一部分

- **与 GPU 对标（1024 输入 + 1024 输出 token）**：

| 指标 | 模型 | LEAP-A | LEAP-D | H100 |
| :--- | :--- | :--- | :--- | :--- |
| 吞吐（tokens/s） | 8B | 202.25 | 446.18 | 274.26 |
| 吞吐（tokens/s） | 13B | 120.62 | **255.17** | 167.51 |
| 能效（tokens/J） | 8B | 19.21 | 20.84 | 0.7836 |
| 能效（tokens/J） | 13B | 11.45 | **11.92** | 0.4786 |
- 13B 上 LEAP-D vs H100：吞吐 **1.52×**，能效 **24.9×**
  - 相对 A100：能效领先 **71.9 倍以上**

- **可扩展性**：模型规模涨 8 倍（1B→8B），关键路径只长约 4 倍 → 吞吐退化是**次线性**的
  - 关键路径由最长水平/垂直通信路由主导，按 se·sl 或 sh·sl 增长，而非 se·sh·sl

- **批处理结论**：
  - 批处理 → TTFT 变好（prefill/decode 重叠减少等待），TPOT 变差（抢 IMC 单元有协调开销）
  - 不是普遍更优，TTFT 敏感场景用批处理，TPOT 敏感场景不用

### **亮点和短板分别是什么？**

四条亮点，五条短板，边界划得很清楚。
- **四大亮点**：
  1. **DSMM / DDMM 分类抽象**干净，可直接迁移到其他 IMC+X 设计
  2. **路由器内做归约**，对症下药解决细粒度切分后的通信瓶颈
  3. **编译期确定性数据流**，换掉运行时仲裁的复杂度和拥塞风险
  4. **片上 PD 分离**，decode 区砍 IMC 换 scratchpad，KV 搬运完全藏进通信流水

- **五条短板**：
  1. batch size 仅 2，只覆盖边缘场景，未碰云端并发问题
  2. 评估是模拟器 + 综合估算组合，IMC 数据取自文献而非实测硅片
  3. 未评估精度，RRAM 8-bit 乘加的器件非理想性、量化误差未讨论
  4. 未提权重写入开销，模型切换、LoRA 动态适配的代价未知
  5. GPU 对标未给出推理框架、并行策略、量化设置，仅作量级参考

### **对国产芯片和 AI Infra 有什么启发？**

三条核心启示，直接对应国内存算一体的普遍卡点。
- **存算一体方向**：
  - 国内团队普遍卡在两点：注意力动态矩阵乘进不了阵列、权重切碎后片上通信失控
  - 这篇把两个卡点摆上台面，还给了可照搬的解法框架
  - 关键预警：别只盯着 TOPS/W 宏单元指标，**互联能耗账要一起算**

- **PD 分离方向**：
  - 软件侧 PD 分离已是标配（DistServe、Mooncake 等）
  - 这篇把思路下沉到片内：同一 die 上做异构分区，prefill 堆权重存储，decode 堆 KV 带宽
  - 新问题：分区比例设计时固定，线上负载比例动态变化，运行时可重配代价未明

- **片上互联方向**：
  - 大规模节点下，集合通信调度质量直接决定系统扩展性
  - 三招不依赖工艺，纯架构/编译功夫，迁移性好：启发式砍映射空间、编译期确定性、计算通信重叠
  - 和 GPU 集群优化 NCCL 是同一个问题在不同尺度的投影

- **落地方向判断**：
  - LEAP 更适合**边缘/端侧**：8B~13B 参数、2048 上下文、batch 2、能效领先 1~2 个数量级
  - 适配场景：本地化智能设备、车载、工业网关等功耗敏感、并发不高的场景
  - 云端落地还需解决 batch 规模、长上下文 KV 容量、多租户隔离等问题

### **📝 补充细节**
- 论文核心结论一句话：存算一体要在大模型上兑现能效承诺，**真正的战场不在存储阵列里，而在阵列之间那张网上**。
- 前作是 ICCAD 2025 的 LEAP 论文，本篇扩展了三块：PD 分离模式、批处理性能分析、IMC/NMC 异构统一设计空间。
- 关键路径拆解显示：IMC 操作很少成为瓶颈，时延主要被 IRCU 内的数据搬运和 DDMM 卡住。
- 64-bit 封包宽度 + 16 路 IRCU 并行的设计点，正好落在 roofline 性能前沿附近。
