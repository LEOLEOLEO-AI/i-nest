# TCCNPU协同路线图

# TCC-NPU 协同落地路线图

> 版本：v1.0 | 日期：2026.08.01 | 基于 TCC 知识库基线 v2.0

---

## 一、背景与目标

### 1.1 为什么要协同

TCC（拓扑中心计算）的核心命题是**「拓扑即计算」**——在通信受限计算中，拓扑的运行时选择与切换直接决定系统性能、能效与可扩展性。当前所有商用智算芯片均为固定拓扑或编译时可配置，无一实现 μs 级运行时拓扑重构。NPU 作为专用算力载体，其固定互连拓扑在面对不同工作负载（训练/推理/信号处理）时存在显著的**「拓扑-原语失配税」**。

TCC 与 NPU 协同的价值在于：**NPU 提供算力底座，TCC 提供液态拓扑能力，二者结合实现「同一硬件底座、不同任务阶段、不同最优拓扑」**。

### 1.2 协同目标

- **短期（1 年）**：完成 TCC 原语与 NPU 计算/互连接口的对齐，在 FPGA 原型上验证单场景拓扑切换
- **中期（2 年）**：在 NPU 芯片中集成 SDI-Lite 交换单元，实现训推一体拓扑切换的端到端验证
- **长期（3 年）**：形成 TCC-NPU 融合架构标准，支撑万级 Tile 规模的液态拓扑计算系统

### 1.3 技术路线原则

- **最小侵入**：TCC 不改变 NPU 内部计算逻辑，通过标准接口对接
- **分层解耦**：R/T/C 三层原语职责正交，对接边界清晰
- **渐进集成**：从软件插件 → 外挂 SDI → 片内集成，逐步深入
- **数据驱动**：每一步都用性能数据说话，不做概念先行

## 二、技术对接架构

### 2.1 整体分层架构

```
┌─────────────────────────────────────────────┐
│  应用层：PyTorch / Megatron / 自研框架        │
├─────────────────────────────────────────────┤
│  编译层：TCC Compiler Pass                   │
│  （通信模式识别 → R/T 原语分解 → Page 选择）  │
├─────────────────────────────────────────────┤
│  通信层：TCC-NCCL Plugin（兼容 NCCL API）     │
├─────────────────────────────────────────────┤
│  拓扑层：SDI 交换矩阵 + 拓扑页 + Page Commit  │  ← TCC 核心
├─────────────────────────────────────────────┤
│  计算层：NPU Tile（SYN 计算核心 + 本地存储）   │  ← NPU 核心
└─────────────────────────────────────────────┘
```

### 2.2 对接的三个接口层

#### 接口层一：硬件原语接口（RTL 级）

TCC 与 NPU 硬件的最底层对接，定义 Tile 级的交互协议。

| 对接项 | TCC 侧角色 | NPU 侧角色 | 接口类型 | 优先级 |
|-------|-----------|-----------|---------|--------|
| **R 原语数据接口** | SDI 交换矩阵提供拓扑路由 | NPU Tile 的数据输入/输出端口 | 数据流接口（AXI-Stream / NoC Flit） | P0 |
| **T 原语计算接口** | T 原语调度与分发 | NPU SYN 计算核心执行 | 控制信号 + 数据通路 | P0 |
| **C 原语控制接口** | CTRL 控制引擎发指令 | NPU Tile 接收同步/切换信号 | 控制信号（中断/事件/寄存器） | P0 |
| **配置总线接口** | Page 配置加载 | NPU 配置寄存器空间 | 配置总线（APB / TileLink） | P1 |
| **时钟同步接口** | 全局/局部时钟分发 | NPU 时钟树接入 | 时钟信号 | P1 |
| **性能监控接口** | 拓扑利用率统计 | NPU 性能计数器 | 寄存器读接口 | P2 |

**R 原语数据接口规范（P0）**：

- 每个 NPU Tile 对外暴露标准的 R 原语接口：输入端口 × N、输出端口 × N
- 数据格式：flit 级，包含 head/flit/tail 标记 + 数据 payload + TopoColor 字段
- 流控：信用量（credit-based）流控，与虚通道绑定
- 拓扑透明：NPU Tile 不需要知道当前拓扑，只需要往指定虚通道发数据

**T 原语计算接口规范（P0）**：

| T 原语 | NPU 侧映射 | 说明 |
|--------|-----------|------|
| T.GEMM | 矩阵乘法阵列 | 直接复用 NPU 的 MAC 阵列 |
| T.FOLD | 累加/规约单元 | 复用 NPU 的 reduce 树 |
| T.MAPS | 向量逐元素运算 | 复用 NPU 的 ALU / 激活单元 |
| T.SCAN | 前缀和/扫描运算 | 需确认 NPU 是否有专用单元 |
| T.LOOK | 查表/索引操作 | 复用 NPU 的 SRAM 接口 |
| T.SPEC | 谱变换/FFT | 复用 NPU 的 FFT 加速单元（如有） |

**C 原语控制接口规范（P0）**：

| C 原语 | 信号类型 | 触发方式 | 作用 |
|--------|---------|---------|------|
| C.TICK | 脉冲信号 | 全局时钟边沿 | 标记 epoch 边界 |
| C.SYNC | 电平信号 | 本地 + 全局确认 | 排空在途数据，建立一致性边界 |
| C.LINK | 脉冲信号 | 配置寄存器写 | 提交新拓扑 Page |
| C.MOVE | 脉冲信号 | DMA 触发 | 触发数据块搬运 |

#### 接口层二：编译栈接口（软件级）

| 对接项 | TCC 侧交付 | NPU 编译器侧对接点 | 交付形式 | 优先级 |
|-------|-----------|-------------------|---------|--------|
| **R/T 原语映射表** | 原语 → NPU 指令/算子的映射规则 | 编译器后端 codegen | 映射规范文档 + 测试用例 | P0 |
| **TCC Compiler Pass** | 通信模式识别 + 拓扑页选择 Pass | 编译器图优化阶段插入点 | MLIR Pass / XLA Pass | P1 |
| **Page 编译器** | 拓扑结构 → SDI 配置位流的编译工具 | 编译器后端配置生成 | 独立编译工具 + API | P1 |
| **调度协同接口** | 拓扑切换与计算调度的协同策略 | NPU 调度器 / DMA 引擎 | 调度接口规范 | P2 |

#### 接口层三：应用框架接口（生态级）

| 对接项 | TCC 侧交付 | 应用侧对接点 | 交付形式 | 优先级 |
|-------|-----------|-------------|---------|--------|
| **NCCL 兼容插件** | TCC-NCCL Plugin | PyTorch DDP / Megatron | 动态库 + 环境变量配置 | P0 |
| **模型适配指南** | 典型模型的拓扑优化方案 | 模型训练/推理代码 | 文档 + 示例代码 | P1 |
| **性能分析工具** | 拓扑利用率分析 + 切换收益统计 | 性能 profiling 工具链 | 工具插件 | P2 |

## 三、SDI 与 NPU NoC 的集成方案

这是硬件对接中最关键的部分——SDI 交换矩阵放在哪里？怎么和 NPU 已有的 NoC 配合？

### 3.1 三种集成模式，从浅到深

#### 模式一：外挂式（Phase 1，FPGA 原型阶段）

```
NPU Chip ──NoC── NPU Tile
   │
  PCIe / 高速 SerDes
   │
SDI FPGA Board（SDI 交换矩阵 + 拓扑页控制器）
   │
  外部互连（以太网 / 光口）
```

- **位置**：SDI 在 NPU 芯片外部，通过 PCIe 或高速 SerDes 连接
- **改动**：NPU 零改动，只需要驱动层适配
- **优点**：风险最低，快速验证
- **缺点**：延迟高（PCIe 级），带宽受限
- **适用**：Y1 原型验证阶段

#### 模式二：Chiplet 级（Phase 2，ASIC 阶段）

```
┌─────────── Package ───────────┐
│  NPU Die   │   SDI Die        │
│  (计算)    │   (交换)         │
│            │                  │
│  ── UCIe / BoW 互连──         │
└───────────────────────────────┘
```

- **位置**：SDI 作为独立 Die，通过 UCIe 3.0 或 BoW 与 NPU Die 封装在一起
- **改动**：NPU 需要增加 UCIe 接口，内部 NoC 做少量适配
- **优点**：延迟低（封装内），带宽高，工艺可分别优化
- **缺点**：封装成本高，Die-to-Die 接口设计复杂
- **适用**：Y2-Y3 产品化阶段

#### 模式三：片内集成（Phase 3，融合架构阶段）

```
┌────────── NPU Die ──────────┐
│  ┌────┐  SDI  ┌────┐       │
│  │Tile│──Matrix─│Tile│       │
│  └────┘        └────┘       │
│     \          /            │
│    SYN 计算核心分布          │
└─────────────────────────────┘
```

- **位置**：SDI 交换矩阵集成在 NPU 片内，替代或补充原有 NoC
- **改动**：NPU 架构级改动，NoC 重新设计
- **优点**：延迟最低（片内），面积效率最高
- **缺点**：改动最大，风险最高
- **适用**：下一代 NPU 架构（Y3 之后）

### 3.2 推荐路径：模式一 → 模式二 → 模式三渐进

- **Y1**：模式一（外挂 FPGA），验证概念和收益
- **Y2**：模式二（Chiplet 级），产品化落地
- **Y3+**：模式三（片内集成），架构级融合

每一步都有明确的退出条件——性能收益达到阈值才进入下一步，避免过度投入。

## 四、TCC-NCCL Plugin 设计

### 4.1 定位与原则

TCC-NCCL Plugin 是 TCC 对接上层生态的核心入口。设计原则：

- **完全兼容 NCCL API**：上层代码零修改
- **透明化拓扑管理**：NCCL 不知道底层拓扑在动态变化
- **最小侵入**：不修改 NCCL 源码，通过插件机制接入
- **性能无损**：插件开销 < 1%，不影响正常通信

### 4.2 插件架构

```
┌──────────────────────────────────┐
│  NCCL 核心（算法 / 协议 / kernel）│  ← 不改动
├──────────────────────────────────┤
│  NCCL 网络抽象层（NET / TRANSPORT）│  ← 插件接入点
├──────────────────────────────────┤
│  TCC-NCCL Plugin                 │
│  ├─ 拓扑需求分析模块              │
│  ├─ Page 选择与调度模块           │
│  ├─ SDI 配置接口                 │
│  └─ 性能监控与反馈模块            │
├──────────────────────────────────┤
│  SDI 驱动 / 拓扑页控制器          │
└──────────────────────────────────┘
```

### 4.3 工作流程

1. **初始化阶段**：
   - NCCL 初始化时，Plugin 加载 SDI 驱动
   - 探测物理拓扑（元拓扑）
   - 预加载标准拓扑 Page Library

2. **集合通信调用时**：
   - Plugin 截获 NCCL 的集合通信请求（AllReduce / AllGather 等）
   - 根据通信类型、消息大小、节点数，从 Page Library 中选择最优拓扑 Page
   - 如果当前拓扑已经是目标拓扑，直接透传给 NCCL，零开销
   - 如果需要切换，触发 Page Commit，切换完成后再执行通信

3. **运行时优化**：
   - 监控实际带宽、延迟、利用率
   - 动态调整 Page 选择策略
   - 记录热点模式，预加载常用 Page

### 4.4 关键技术点

- **快速路径优化**：常用通信模式（如固定大小的 AllReduce）走缓存路径，不需要每次都做决策
- **预加载与双缓冲**：预测下一个通信模式，提前加载目标 Page 到 shadow 寄存器
- **回退机制**：如果 SDI 出现故障，自动回退到标准 NCCL 路径，不影响业务运行

## 五、里程碑计划（三年）

### Y1：原型验证年（2026.07 — 2027.06）

**目标**：完成 TCC 原语与 NPU 接口对齐，在 FPGA 原型上验证单场景拓扑切换。

| 里程碑 | 时间 | 交付物 | 验收标准 |
|-------|------|--------|---------|
| M1：原语接口对齐 | 第 1-3 月 | 《Tile 接口规格书 v1.0》 | 双方签字确认 R/T/C 原语接口定义 |
| M2：SDI-Lite FPGA 原型 | 第 4-6 月 | SDI-Lite FPGA 比特流 + 驱动 | 4R+3T 原语功能正确，单 Page 通信正常 |
| M3：NPU 外挂集成 | 第 7-9 月 | FPGA-NPU 联合仿真平台 | 跑通 R.FUSE（AllReduce）端到端流程 |
| M4：Page Commit 验证 | 第 10-12 月 | Page Commit 测试报告 | 16 节点切换时延达到目标量级（< 1μs） |
| M5：单场景性能对比 | 第 12 月 | 性能基准测试报告 | 固定拓扑 vs 动态拓扑，至少一个场景有 > 20% 性能提升 |

**Y1 关键风险与对策**：
- 风险：NPU 接口不开放，外挂集成困难
- 对策：先用 NPU 的标准接口（PCIe + 现有 NoC），不要求 NPU 团队改硬件；性能数据出来后再谈深度集成

### Y2：场景闭环年（2027.07 — 2028.06）

**目标**：实现推理、AllReduce、LoRA 闭环、16 波束 DBF 四个场景验证，TCC-NCCL Plugin 可用。

| 里程碑 | 时间 | 交付物 | 验收标准 |
|-------|------|--------|---------|
| M6：TCC-NCCL Plugin v1.0 | 第 13-15 月 | Plugin 动态库 + 文档 | 兼容 NCCL 2.x API，标准 AllReduce 测试通过 |
| M7：训推一体切换验证 | 第 16-18 月 | 训推一体测试报告 | 训练（Butterfly）↔ 推理（Pipeline）切换 < 5μs，性能提升 > 30% |
| M8：LoRA 微调场景 | 第 19-21 月 | LoRA 适配方案 | LoRA 微调场景下拓扑切换收益验证 |
| M9：16 波束 DBF 场景 | 第 22-24 月 | DBF 适配方案 | FFT/DBF 信号处理场景验证 |
| M10：Chiplet 方案设计 | 第 24 月 | SDI Die 规格书 | SDI 作为独立 Chiplet 的架构设计完成 |

**Y2 关键风险与对策**：
- 风险：NCCL Plugin 性能开销过大
- 对策：快速路径优化 + 预加载机制，确保插件开销 < 1%；大消息场景下开销占比天然低

### Y3：产品化与标准化年（2028.07 — 2029.06）

**目标**：完成 64×16 DBF、FFT↔DBF 切换，推动标准与开源工作，形成产品规格。

- 风险：大规模扩展后一致性时延不可控
- 对策：三级一致性域设计，分层优化；最终一致性降级方案兜底

## 六、组织对接策略

### 6.1 对接团队与角色

| TCC 侧角色 | NPU 侧对接人 | 对接内容 | 频率 |
|-----------|-------------|---------|------|
| 架构师 | NoC / 互连架构师 | 硬件接口、SDI 集成方案 | 双周 |
| 编译器工程师 | 编译器后端负责人 | Compiler Pass、原语映射 | 双周 |
| 软件工程师 | 驱动 / 运行时负责人 | NCCL Plugin、驱动适配 | 周会 |
| 性能工程师 | 性能架构师 | 性能基准、优化方向 | 月会 |
| 项目负责人 | NPU 项目总监 | 里程碑、资源协调 | 月会 |

### 6.2 推进策略

**第一步：找到痛点，单点突破（前 3 个月）**

不要一上来就谈"范式革命"。先做一件事：
- 找一个 NPU 团队公认的性能瓶颈场景（比如某个 AllReduce 密集型模型效率只有 60%）
- 用 TCC 的思路做一个仿真或 FPGA 原型，证明动态拓扑能把效率提到 90%+
- 拿着数据去找 NPU 团队谈合作

**第二步：建立联合工作组（3-6 个月）**

有了数据之后，成立联合工作组：
- 双方各出 2-3 人，全职投入
- 明确共同目标（比如"Y1 底完成 FPGA 原型验证"）
- 建立周会机制和问题跟踪

**第三步：从软件到硬件，逐步深入（6-18 个月）**

- 先做软件插件（NCCL Plugin），不需要 NPU 改硬件
- 再做驱动级适配，小范围改动
- 最后做硬件级集成，架构级改动

每一步都有明确的收益数据支撑，让 NPU 团队愿意投入更多资源。

### 6.3 沟通中的三个"不要"

- **不要否定 NPU 现有架构**——要说"在现有基础上增加一个优化维度"
- **不要拿概念当证据**——拿性能数据说话，数据是最好的说服工具
- **不要贪多求全**——先做好一个场景，再扩展到更多场景

## 七、风险与应对

| 风险类别 | 具体风险 | 概率 | 影响 | 应对措施 |
|---------|---------|------|------|---------|
| **技术风险** | Page Commit 时延达不到目标量级 | 中 | 高 | 分层优化：片内硬件同步、片间树形归约、机架间最终一致；不追求全规模强一致 |
| **技术风险** | SDI 面积 / 功耗开销过大 | 中 | 中 | 从 SDI-Lite 开始，只支持必要的原语；工艺优化（SDI 用先进工艺，NPU 用成熟工艺） |
| **集成风险** | NPU 接口不开放，对接困难 | 高 | 高 | 外挂式集成（PCIe/FPGA）先行，不依赖 NPU 内部接口；用数据推动深度集成 |
| **生态风险** | NCCL Plugin 兼容性问题 | 中 | 中 | 充分测试，覆盖主流 NCCL 版本；提供回退机制，故障时自动切回标准 NCCL |
| **组织风险** | NPU 团队配合意愿低 | 中 | 高 | 找到 NPU 团队的痛点，用收益数据驱动；从基层工程师开始建立信任，逐步向上推进 |
| **市场风险** | 动态拓扑的价值不被市场认可 | 低 | 高 | 聚焦训推一体等明确场景，用可量化的收益说话；推动标准和开源，建立生态 |
