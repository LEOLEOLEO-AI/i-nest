# FBLayout 深度解析：用 Tile 级内存布局让手机 GPU 跑 LLM 微调快 5.7 倍

### 🏆 这篇论文解决了什么核心问题？

端侧 LLM 微调在移动 GPU 上**效率极低甚至不如 CPU**，根源是前向-反向传播的内存布局冲突。
- **反直觉现象**：推理时移动 GPU 比 CPU 快约 **6.5 倍**，但微调时优势消失，ViT 模型上 GPU 甚至比 CPU **慢 43%**。
- **内存压力**：训练内存占用是推理的 **7 到 10 倍**，即便用 LoRA 和激活重计算依然紧张。
- **速度痛点**：移动 CPU 上微调 1B 模型单步超 **50 秒**，数千步需数小时到数天，还会触发热节流。

### 🧩 为什么移动 GPU 训练会这么慢？

**前向和反向访问同一张量的方向相反**，线性布局只能保证一个方向高效。
- **冲突本质**：前向 MatMul 沿 K 维归约，反向沿 M 维归约 → 链式法则天然引入转置，reshape 进一步加剧维度不匹配。
- **移动 GPU 特殊性**：采用 **2.5D 纹理内存**（二维坐标 + RGBA 四通道），纹理缓存为二维空间局部性优化，跨步访问代价被放大。
  - 行主序吞吐量是列主序的 **1.6 倍**，大张量下差距可达数倍。
  - 布局冲突时 ALU 利用率可低至 **15% 以下**，大部分时间在等内存。

### ⚖️ 现有方案为什么不行？

两种主流策略**都有致命缺陷**，要么牺牲反向效率，要么转换开销太大。

| 策略 | 代表框架 | 问题 |
| :--- | :--- | :--- |
| 布局复用 | MNN | 反向内存访问碎片化，延迟达最优布局的 **5.31 倍** |
| 显式转换 | TFLite | 布局转换占运行时间 **40.8%–50%**，内存分配占 20%–50% |

说白了，现有框架要么让反向跑不快，要么把一半时间花在"把数据摆成反向能读的样子"上，两头都不讨好。

### 🧠 FBLayout 的核心洞察是什么？

**矩阵乘法不同归约方向加载的是同一批 Tile 元素**，只是聚合顺序不同。
- **Tile 不变性**：前向沿 K 归约、反向沿 N 归约，访问的权重 Tile 集合完全一致，仅 Tile 内遍历方向不同。
- **破局思路**：只要 Tile 内元素在任意方向都连续，单一布局就能服务所有归约方向，不需要物理转换。

### 🛠️ FBLayout 由哪几部分组成？

整套系统分**四个阶段**，从图分析到全局布局优化逐层推进。
- **系统总流程**：联合前向-反向训练图 → 图分析 → R-Tile 布局设计 → 基于 Tile 的索引变换消除 → 激活引导全局布局选择 → 优化后的 R-Tile 训练图。

#### 1. 算子分类：先把问题拆清楚

按两个维度把算子分成四类，精准定位冲突来源。
- **分类维度**：前向张量依赖性（反向是否需要前向张量） + 访问模式一致性（前后向访问模式是否相同）。
- **四类算子**：
  - **FTI-C（无关+一致）**：Add、Subtract、Scale 等逐元素算子 → 无布局约束。
  - **FTD-C（依赖+一致）**：ReLU、Sigmoid、Softmax、Dropout → 前向高效的布局反向也高效。
  - **FTI-D（无关+发散）**：Transpose、Permute、Reshape → 访问发散但不依赖前向值。
  - **FTD-D（依赖+发散）**：MatMul、Conv2D、BatchNorm、LayerNorm → 布局冲突的核心，最关键。

#### 2. R-Tile：面向多维归约的统一布局

利用移动 GPU 二维纹理内存特性，让任意归约方向都落在缓存块内。
- **Tile 形状候选生成**：三层约束剪枝，不用穷举搜索。
  - **C1 计算对齐**：Tile 维度是 warp 大小整数倍（Mali 32，Adreno 64）。
  - **C2 内存对齐**：能放入 L1 纹理缓存，与 64 字节缓存行对齐。
  - **C3 形状兼容**：优先整除张量维度，填充率低于 10% 才保留。
- **两级物理映射**：
  - **Tile 内映射**：小 Tile 用行主序，大 Tile 用 2D 分块，最小化缓存块覆盖数。
  - **Tile 间映射**：按行主序排列，Tile 数量多的维度放水平方向（匹配纹理缓存更宽的水平跨度）。
- **效果**：沿 Dim2 归约时走 Z 字形路径，仍在单个 2D 缓存块内，带宽浪费极小。

#### 3. 基于 Tile 的索引变换消除

**只搬坐标不搬数据**，把物理变换变成编译时的索引重映射。
- **核心观察**：Transformer 中绝大多数变换（reshape、transpose）只重排 Tile 位置，不改变 Tile 内部结构。
- **合法性三检查**：
  - R-Tile 维度依赖：前置变换保持 Tile 维度。
  - Tile 边界保持：拆分维度与 Tile 边界对齐。
  - Tile 内连续性：最内层维度保持 stride-1。
- **消除方式**：通过预计算的 Tile 级线性映射，把 O(元素数)的内存操作降为 O(Tile 数)的整数运算。
- **覆盖率**：LLM 中超过 **95%** 的变换可被消除，剩余回退仅占总运行时间不到 6%。

#### 4. 激活引导的全局布局选择

让**布局冲突最剧烈的节点**决定全局布局，其他节点自适应。
- **传播规则**：
  - FTD-D 算子（如 MatMul）是锚点，R-Tile 布局强制向外传播。
  - FTI-D 算子（变换类）直接被索引消除吸收。
  - FTI-C/FTD-C 算子灵活适配传入布局。
- **连续 FTD-D 处理**：连续 MatMul 链用贪心搜索，按输入张量大小排序，优先满足大张量的布局偏好，仅在有益时插入变换。

### 📊 实验效果到底有多好？

在 7 款模型、两类移动 GPU 上**全面碾压**现有框架。
- **端到端加速**（相对 MNN/TFLite/TVM）：
  - 解码器-only LLM：**3.9–5.7 倍**。
  - 编码器-only：2.2–5.2 倍。
  - 编码器-解码器：2.3–4.7 倍。
- **资源效率**：
  - 全局内存访问量降低 **3.5 倍**，缓存未命中减少 **4.2 倍**。
  - 能耗降低 **3.5 到 6.3 倍**。
- **编译时间**：从 MNN 的 723 秒、TVM 的超 4800 秒，骤降至 **6.1 秒**。
- **可移植性**：Adreno 730 上加速 1–5 倍，Mali G925 上加速 1.5–7.3 倍，适配新 GPU 仅需一次性硬件特性刻画（21–26 秒）。

### 📈 各优化组件分别贡献多少？

三层优化**互补叠加**，每一层都有明确收益。
- **仅 R-Tile**：平均 1.88 倍加速，内存访问减少 2.50 倍。
- **+ 索引消除**：再提升 1.45 倍，内存访问再减 1.86 倍。
- **+ 全局布局选择**：再贡献 1.31 倍加速，内存读取再减 1.56 倍。

### 📝 补充细节
- **论文地位**：MobiSys 2026 首篇专门针对移动 GPU 大语言模型微调加速的系统工作。
- **实现基础**：在 MNN 之上构建，约 9.2K 行 C++ 和 OpenCL 代码。
- **精度保证**：仅优化数据访问和计算效率，不改变模型架构、精度或训练目标，微调精度与基线完全一致。
- **评估模型**：Llama3.2-1B、Qwen2.5-1.5B、Gemma2-2B、BERT-Large、ViT-Large、Whisper-Large、Stable Diffusion v1.5。
