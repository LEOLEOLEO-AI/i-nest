# 重新设计：五条工作流统一管理

> 触发：用户指出「当前每日剪入的内容太多，但能对科研起到有效促进的内容太少；
> 科研看板和主页也没用起来，无法有序推进后续工作」，要求按五项功能重新设计：
> ①论文与专利撰写 ②项目指南编写 ③论文阅读与复现 ④核心代码编写与验证
> ⑤复杂网络涌现智能仿真（含秀丽线虫等交叉仿真），并搭建仿真与验证平台。

---

## 一、诊断修正：问题不是"内容太多"，而是"没有分诊"

我一开始也以为是量的问题。**实测推翻了它**：

| 入口 | 存量（实测） | 抽查结论 |
|---|---|---|
| `GetNotes_Inbox` | **719** 个文件 | 抽查前 10 个：《拓扑中心计算网络底座项目建议书》《JX-N1端侧网算融合智能计算芯片产品定义方案》《iNEST体系第一性原理诊断报告》《高端AI芯片晶上系统方案项目指标讨论会议》—— **全是高价值材料** |
| `20_Processing` | 905 | 加工层 |
| `00_Inbox/_pipeline_insights` | 240（近 14 天 26） | 论文管线洞察 |
| `00_Inbox/02_网页剪藏` | **0** | 微信剪藏通道实际是空的 |
| `00_Inbox` 其余 | ~14 | — |

**所以真正缺的不是"少收"，而是"分诊（disposition）"**：没有任何一步把输入判成
「属于哪条工作流 / 现在能不能动手 / 不相关就明确拒掉」。内容进来后只是堆着，
既没被拒、也没变成动作，于是"看得多、推进少"。

同理，看板没被用起来，不是因为它不存在（`70_Dashboard/` 有 index.html、data.js、
task_board.json 27KB），而是因为它**只报统计数字，不告诉人现在该动手做什么**。

## 二、重新设计：三层结构

```
① 分诊层  triage.py        891 条入口 → 今天 15 条（其余 park/reject，且记住 reject）
                 ↓
② 工作流层 workstreams.py  五条流，每条有 输入/产物/闸门/闭环定义
                 ↓
③ 执行层  各流的具体工具     paper_reader / zotero_bridge / sim_platform / 门禁
```

### 2.1 分诊层 —— 直接解"内容太多、有效太少"

`research_evolve/triage.py`：对每个入口条目做三态判定。

| 结果 | 判据 | 实测数量 |
|---|---|---|
| **keep → 今天** | 领域相关 **且** 是交付物形态（建议书/指南/交底书/草稿…）或含显式待办（`- [ ]`/TODO/待补） | **15（硬上限）** |
| keep → 积压 | 同类，排在后面 | 105 |
| park | 领域相关但不是待办/交付物，属参考材料 | 754 |
| reject | 命中排除词，或噪声信号且无领域词 | 18（并记住，后续不再扫） |

**891 条输入 → 今天 15 条。** 这个比例就是分诊要的效果。

过程中修掉三处精度缺陷（都是实测暴露的）：
1. **动作词太宽**：首版含"报告/计划/实验/代码"，891 条判出 **261 条 keep** —— 等于没分诊。
   收紧为"交付物形态 + 显式待办"后降到 120。
2. **模板/日报被当成待办**：收紧后排名前两位变成 `_TEMPLATE_digest` 和
   `2026-08-02_arXiv日报_9篇`（它们含 `[ ]` 和 `draft` 字样）。加 feed/template 排除后精确了。
3. **工作流误判**：项目指南被判成 CODE。第一次给标题 ×3 权重 —— **仍然**误判，
   因为一部长篇指南正文能命中十来个 CODE 词，权重压不住。
   最终改为**字典序**：先比标题命中数，标题打平才比正文。GUIDE 从 2 条升到 7 条且判对。

另加**同名归并**：库里存在大量 `X.md` / `X_2.md` 副本对，不合并的话
"今天 15 条"里一半是同一份东西，白白占配额。

### 2.2 工作流层 —— 解"无法有序推进"

`research_evolve/workstreams.py` 定义五条流，每条给出四件事：

| 流 | 闭环定义（什么算做完） | 关键闸门 |
|---|---|---|
| **PAPER** 论文与专利撰写 | 提交一次完整稿（引用核验通过 + 数字全带标签） | 引用只能取自 papers.yaml 白名单；性能数字必须带 `[实测]/[仿真]/[引用]/[推导]/[假设]/[待测]` |
| **GUIDE** 项目指南编写 | 一份可提交的指南，指标全部有验证方式 | 每条技术指标必须有验证方式与验收标准（对应 V-* 任务） |
| **READ** 论文阅读与复现 | 一篇论文：笔记 + 一键复现脚本 + 与原报告的差异说明 | 结论带页面级出处（citekey + 页码）；复现要留种子与依赖版本 |
| **CODE** 核心代码编写与验证 | 一个实验：单一规范脚本 + 可复现 manifest + 验收通过 | **一个实验只有一个规范版本**；固定种子 + 锁依赖 + run_manifest |
| **SIM** 复杂网络涌现智能仿真 | 登记 + 可复现 + 有基线对照 + 结论带 `[仿真]` | 区分 `[仿真]`/`[实测]`；实验必须进注册表 |

### 2.3 执行层 —— 已有的四个工具 + 新建的仿真平台

| 工具 | 服务的流 | 状态 |
|---|---|---|
| `zotero_bridge.py` | READ / PAPER | ✅ 540 条 / 100% BBT key / 268 PDF，已接入每日 04:30 |
| `paper_reader.py` | READ | ✅ 268 篇 / 22489 块索引；引用抹除 + 弃答 + 页面级溯源 |
| `research_evolve/gates.py` | PAPER 闸门 | ✅ 门禁通过（新增违规 0） |
| **`sim_platform/`** | **SIM** | ✅ **本轮新建**（见第三节） |

## 三、仿真与验证平台（`90_System/sim_platform/`）

### 3.1 先做数据体检 —— 查出两个"假数据"

平台第一件事是把各物种连接组统一成同一个 `(adj, meta)` 契约。这一步就查出问题：

| 数据 | 宣称 | **实测真相** |
|---|---|---|
| `iNEST_Sim/data/aconnectome.json` | C. elegans | ✅ 真数据：300×300 化学突触（非零 2276）+ 300×300 电突触（非零 1096）+ 符号位 |
| `connectome/macaque_rm_weights.txt` | 猕猴 | ✅ 真数据：82 节点 / 3312 边 |
| `connectome/hemibrain_edges.csv.gz` | 果蝇 hemibrain 边表 | ❌ **715 字节，内容是 Google Cloud 的 `AccessDenied` 报错页** —— 把错误页当连接组存了下来 |
| `connectome/allen_mouse_connectivity.json` | 小鼠连接组 | ❌ 3.27 MB，实为 Allen Institute 的**实验目录元数据**（2992 条记录：data_set_id / specimen_name / injection_x/y/z），**不是连接矩阵** |

平台现在**明确报出**这两条不可用及原因，而不是静默返回空或拿垃圾算出结果。
（顺带全库扫描确认：这类"错误页当数据"只有 1 个文件，未扩散。）

### 3.2 可复现运行器

`harness.run()` 每次落 `run_manifest.json`：**随机种子、配置哈希、依赖版本、
git 提交、结果哈希、Python/平台版本、耗时**。任何结论可追溯、可重跑，
报告里直接给出复现命令。

### 3.3 治理"版本蔓延" —— 实测 39 个多版本文件

`sim_platform.run lint` 实测：

| 实验 | 并存版本数 |
|---|---|
| `sdi_experiment1` | **23**（v2…v19 + v12b + v12c + v17b + final + universal） |
| `sdi_experiment5` | 11 |
| `sdi_experiment7` | 5 |

这直接违反 AGENTS.md 的可复现要求：说不清哪个有效、无从判断结论出自哪个版本。
平台对策：**一个实验只有一个规范脚本**，历史版本交给 git，注册表只记录"版本事件"。

> 修掉自己的一个 bug：lint 首版用 `(?=\.py$)` 前瞻去匹配 `stem`（无扩展名），
> 前瞻永不成立，于是**39 个多版本文件被报成"未发现多版本"**。改为匹配 stem 末尾后正常。

### 3.4 首个实验：跨物种临界性交叉仿真

`experiments/celegans_cross_species_criticality.py` —— 这就是"交叉仿真"的落点：
同一套度量同时跑在 C. elegans（化学/电突触）与猕猴连接组上。

σ（代际分支比）随增益的走向（实测）：

```
celegans       gain 0.02 → σ=0.476 ... gain 1.0067 → σ=0.995   τ=1.21
celegans_elec  gain 0.02 → σ=0.182 ... gain 1.0067 → σ=0.995   τ=1.21
macaque        gain 0.02 → σ=0.036 ... gain 1.5    → σ=0.973   τ=1.35
```

**修掉一个会让结论完全错掉的 bug**：首版把"命中的邻居数"当后代，但命中里包含
**已被激活**的节点（它们不产生下一代），结果最低增益下 σ 仍报 3.916，
于是"临界增益"被误判到扫描区间最左端，跨物种对照结论随之无效。
改为只统计**新增激活**、按代际比求 σ 后，σ 才正确地随增益穿越 1。

### 3.5 诚实声明：σ≈1 在 C. elegans 上是有限尺度饱和

平台自动检出：`celegans` 与 `celegans_elec` 在高增益段 `<S>` 已顶到节点总数
（300 全部被激活），**此时 σ≈1 是有限尺度效应，不是临界的证据**。
正确做法需要**子采样**（标准神经元雪崩分析做法）或做有限尺度标度（多 N 对比），
**本实验尚未实现**，故不能把 σ≈1 当作临界态证据。

τ 也只用于同一实验内不同增益的相对比较，未做 KS 检验，不声称精确拟合。
—— 这三条已写进实验的 `limitations` 字段随结果一起落盘。

## 四、两个核心问题的对应关系

| 用户反馈 | 根因（实测） | 对策 | 实测效果 |
|---|---|---|---|
| 剪入内容太多、有效太少 | **没有分诊这一步**；719 个高价值文件堆在入口层无人处置 | `triage.py` 三态分诊 + 每日硬上限 + reject 记忆 | **891 → 今天 15 条** |
| 看板/主页没用起来 | 看板只报统计，不报"现在该做什么"；五条流没有状态机与闭环定义 | `workstreams.py` 给每条流定义闭环与闸门；分诊输出直接是带勾选框的行动清单 | 每天只需打开一页 |
| 版本蔓延、复现困难 | 同一实验 39 个多版本并存 | 注册表 + lint 体检 + run_manifest（种子/配置哈希/依赖/结果哈希） | lint 已能定位全部 39 个 |
| 仿真数据不可信 | 有文件把云存储报错页当连接组存下来 | 平台加载时做数据体检并**明确报错** | 查出 2 个假数据 |
